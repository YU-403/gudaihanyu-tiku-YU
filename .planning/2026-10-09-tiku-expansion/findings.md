### 三、"章节"如何进入页面（机制实测）

构建脚本：`C:\Users\YU\.codex\skills\quiz-complete\build.py`

- `md_files = sorted([... os.walk(input) ...])`（build.py:3376）——递归扫描，按完整路径字符串排序。
- `section_name = re.search(r'^#\s+(.+)$', content, re.MULTILINE)`（build.py:3308）——
  **章节名取自文件第一行的 H1 标题，不是文件名**；无 H1 时回退为文件名。
- `section_map[section_name] = 该文件题目的索引区间`（build.py:3417），无题的文件不登记。

因此新增章节的操作只有一步：**在对应目录放一个新的 `.md`**。

| 模式 | 数据来源 | 新增后表现 |
|:--|:--|:--|
| 专题模式 | `sectionMap` 的键（每个 `.md` 一条） | 列表多一条，标签为 H1 标题 |
| 知识点专项 | `**知識回溯**` 字段，按章节分组成树 | 多一组，组内为该章标签 |
| 随机 / 生涯 / 错题 / 考试模拟 | 全库题目池 | 自动纳入 |

**注意**：专题模式的 32 条是**平铺一层**，模板未使用目录层级做分组——
`常用词部分\`、`通论部分\`、`文选部分\` 只影响文件读取顺序，不产生「三大板块」二级结构。
这一点与仓库 README 的描述不一致（README 写的是两级）。

### 九、Phase 2 实测：构建链路的三处机制真相（2026-10-09）

#### 1. `--custom-css` 不是「追加到样式表末尾」

模板中 `__STYLE_CSS__` 占位符位于 `<style>` 区块**前部**（build.py 第 345 行，紧接 reset 规则），
替换语句为：

```python
html = html.replace('__STYLE_CSS__', style['css'] + (('\n' + args.custom_css) if args.custom_css else ''))
```

故自定义 CSS 落在 `style['css']`（含 `:root` 变量）之后、**全部组件规则之前**。
后果：`:root` 变量覆盖有效（与组件规则无同选择器冲突），
但任何与模板同选择器的规则覆盖都会被其后的模板规则打败。

> 仓库根目录 findings.md 第八节曾称该参数「只是把参数文本拼在样式表最后」，结论有误——
> 当年之所以成功，是因为旧版棕色系只覆盖了 `:root` 变量，未触及规则。

**处置**：本项目主题层改由 `rebuild.ps1` 在构建后追加到 `</style>` 之前，语义上真正「后写胜先写」。

#### 2. `<style>` 是 raw-text 元素，主题内不能出现样式结束标签字面量

主题文件开头说明注释里写了样式结束标签，浏览器会在该处**提前闭合 `<style>`**，
其后全部 CSS 会作为正文文字渲染出来。已在 `rebuild.ps1` 加断言拦截，并在主题文件顶部注明约束。

#### 3. 判断题内部比对值：v2.11 是简体字面量，不是 `T`／`F`

| 版本 | 机制 |
|:--|:--|
| v2.10（重建前的 index.html） | 内部值用 ASCII 占位符 `'T'` / `'F'` |
| v2.11（当前模板） | `[[JUDGE_TRUE_LABEL, '正确'], [JUDGE_FALSE_LABEL, '错误']]`——显示用繁体常量、比对用简体字面量 |

功能等价（实测断言：按钮值集合 == 题库答案取值集合）。差别是 v2.11 依赖「片段级白名单不会转换该字面量」，
比 v2.10 的 ASCII 占位符脆弱一档，但当前构建正确。

#### 4. 答案位置均衡会暴露「解析引用选项字母」的题

重建时 v2.11 的答案位置均衡重排了 163 道单选，脚本自动告警 2 道题的解析引用了选项字母：
通論三「單純複音詞」、通論二「古今意義毫無關係的詞」。后者实际被重排
（答案 C→D，解析仍写「B項…（供給→給予）」），已是事实性错误。

**处置**：两题解析改写为按内容指称，不再引用字母，从此对选项顺序免疫。
题干未动 → 题目 ID 不变 → 用户进度不受影响。

#### 5. 既有的一处死规则（本次原样保留）

`.stat-card` 的角线装饰（在主题层内）排在 `.stats-grid/.stat-card` 版面规则**之前**，
后者用了 `background:` 简写，会把 `background-image` 重置为 none——
即已验收版本里统计卡的角线本就是不可见的死规则。本次按「忠实还原」原则保留原样，
若要修需调整两条规则的相对顺序（属视觉改动，另行确认）。

### 十一、核字流程首战：两处 OCR 引擎互证（2026-10-09）

出校准题时，教材 OCR 里「《七月》第四章以『蜩』押『萋』（幽宵合韻）」一句引起怀疑：
《七月》第四章并无「萋」字，且紧随其后的讲解是「大約就是用 eu 押 au」——
「萋」属脂部，与 au 不符，逻辑上讲不通。

**核字过程（可复用）**：

1. 两份 OCR 文本（`full.md` 与同名 `.md`）措辞一致、怀疑的对象相同 → 不是抄录问题
2. 全四册 PDF **无文字层**（1855 页扫描件），无法直接检索
3. 改用 MinerU 的 `content_list_v2.json` 反查物理页：该段在分册 PDF 第 175 页（0 起算 174），
   其 `bbox` 为 **0–1000 归一化坐标**（非 0–1、非像素）
4. 用 PyMuPDF 按 bbox 裁切该段，再以 **600 dpi 逐行渲染**，交给独立引擎（Tesseract.js，`ocr-local` skill）识别

**结果**：Tesseract 读出「以『時』押『要』（幽宵合韻）」——「要」即「葽」掉了草字头，
「時」即「蜩」；MinerU 作「蜩／萋」，两家一致的是「蜩」。结合三条硬证据定案：

| 证据 | 说明 |
|:--|:--|
| 篇内用字 | 《七月》第四章「四月秀葽，五月鳴蜩」——「葽」正在其中 |
| 韵部 | 蜩属幽部、葽属宵部，正是「幽宵合韻」 |
| 讲解自证 | 「用 eu 押 au」——蜩＝eu、葽＝au，逐字吻合 |

**结论**：教材原文为「『蜩』押『葽』」，MinerU 的「萋」是 OCR 误字。已据此修正校准题第 7 题的选项与解析。

> 本段同一次 OCR 还错了两处：《關雎》五章的「芼」作「苇」（注文却把「芼」释作 mào），
> 《靜女》三章的「貽」作「貯」（同书文選正文作「美人之貽」）。这两处可由篇内正文互证，
> 不必翻页；「葽」因正文本身也被误作「菱」才需要走到渲染核字这一步。
